# 技术复盘写作

根据仓库、提交记录或开发日志撰写技术复盘，尤其是以开发 Agent 视角成文时读取本文件。目标是写出有证据的工程判断，而不是功能宣传稿。

## 1. 先读实现，再定文章主线

按需要读取：

1. 默认分支、README 与当前版本；
2. 核心源码和真实执行路径；
3. 测试、构建脚本与验证材料；
4. 开发日志和关键提交，用来还原问题与结论的变化。

建立“当前事实”和“历史纠偏”两条笔记。文章内容必须能追溯到实现、故障现象或验证记录；不要先套模板再寻找材料填充。

## 2. 使用参与者的第一人称

当开发 Agent 实际承担了分析或实现时，用“我”描述设计判断、错误和修正，但不要写成自我表彰。

- 写清“我为什么这样选”，而非“我很厉害地完成了”。
- 真机验收由用户完成时，明确其验证角色，不把结果写成 Agent 亲自执行。
- 不必在首句宣布“作为开发 Agent”；让视角通过具体判断自然成立。
- 不把推测写成经历，不补造对白、故障细节或心理活动。

## 3. 从具体问题开头

用一至两段完成：最初需求、实际复杂性、当前版本和文章范围。避免仪式化的身份介绍。

**不推荐：**

> 这次我作为开发 Agent，参与完成了某个项目……

**推荐：**

> 这个项目最初要解决的问题很简单：用户改密后自己恢复网络驱动器。真正做起来才发现，几条映射命令只覆盖了最理想的情况，更多工作量都花在状态判断、失败处理和重启验证上。

项目特有细节只作示例。其他文章应使用自己的真实问题，不要替换名词后复用整段。

## 4. 按工程判断组织正文

以下是一种常用顺序，不是固定目录：

> 需求与状态 → 约束和技术取舍 → 核心流程 → 关键边界 → 故障纠偏 → 测试与验收 → 可迁移经验

每节尽量形成完整链条：

> 遇到什么问题 → 有哪些约束 → 为什么选择当前方案 → 如何验证 → 仍有哪些边界

优先选择有决策价值的章节，不为“架构、功能、亮点、总结”凑齐栏目。读者应能理解方案背后的原因，而不只是看到最终功能列表。

## 5. 把纠偏写成证据链

被测试或真机推翻的结论具有很高价值。按以下顺序表达：

> 旧结论或实现 → 观察到的异常 → 根因或旧假设失效之处 → 新方案 → 新验证标准

- 明确旧结论已被取代，避免与当前说明并存成矛盾。
- 不因追求“专业感”而隐去合理试错，也不把错误渲染成戏剧故事。
- 若根因尚未闭环，使用“当前证据指向”等准确表述，不伪造确定性。

## 6. 准确表达测试与可靠性

- 区分确定性回归、结构守卫、构建成功、真实环境测试和重启验收。
- 写出测试数量前先实际计数或核对记录，并说明适用配置。
- 不用“全部测试通过”推导出“所有环境都没有问题”。
- 涉及操作系统行为时，分别验证当前结果与重连、重启等后续状态。
- 可复用的验收标准比“在我这里能跑”更值得保留。

## 7. 控制代码与细节密度

- 只展示能解释核心机制的最小命令或代码片段。
- 私有仓库中的内部地址、域名、账号和密钥不进入公开文章；替换为通用示例。
- 不用大段源码代替解释，也不为了简短删掉关键前提。
- 对安全能力使用有限表述，例如“不写日志、不落盘”，不要扩展成无法证明的绝对安全承诺。

## 8. 收束到可迁移原则

结尾只保留对下一个项目仍有帮助的原则，例如状态先于动作、破坏性操作限定范围、查询失败不等于空结果、当前可用与重启可用分别验证。

避免重复各节内容、追加未确认的待办，或用口号替代实际结论。

## 完成前自问

- 开头是否直接进入了真实问题？
- 每个重要结论是否有实现或验证依据？
- 第一人称是否符合实际贡献？
- 是否讲清了至少一个关键取舍或纠偏，而不只是功能清单？
- 当前行为与历史方案是否清楚分开？
- 公开示例是否完成脱敏？
- 删除任意空泛段落后文章是否反而更好？若是，删掉它。

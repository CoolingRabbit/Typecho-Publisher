# Typecho 操作参考

执行文章管理或发布操作时读取本文件。所有命令均从当前技能目录调用 `typecho-cli`。

## 前置条件

- 博客已安装 Typecho-Publisher 插件 v4.1.0 或兼容版本。
- 站长已为本 Agent 对应账户生成 AI Token。
- 按主文件所述优先级完成 `domain` 与 `token` 配置；不要在命令回显、文章或日志中暴露凭据。

## 配置预检

- 已知配置有效时直接进入任务；配置状态未知时，先单独执行 `categories`，同时验证配置并获取现有分类。
- 预检成功前不要并行执行 `list` 等其他业务请求，避免同一配置问题造成多次无效调用。
- `categories` 报告缺少配置时，可以将 `config.example.json` 复制为技能目录的 `config.json` 并填写真实配置，也可以写入 `~/.config/typecho-cli/config.json`。不要直接要求用户重建 Token，不得回显凭据。

```bash
cp <技能目录>/config.example.json <技能目录>/config.json
chmod 600 <技能目录>/config.json
```

- 真实 `config.json` 不得提交到仓库或打入公开分发包。
- 返回 401 时按认证错误处理，不要用恢复配置代替 Token 有效性检查。
- 其他预检失败先处理对应的网络或配置问题，再进入查重和发布流程。

## 命令

```bash
# 查询文章列表
python3 <技能目录>/typecho-cli list [--page N] [--page-size N] [--status STATUS] [--category CATEGORY]

# 查询单篇文章
python3 <技能目录>/typecho-cli get --cid <文章ID>

# 查询现有分类
python3 <技能目录>/typecho-cli categories

# 创建文章
python3 <技能目录>/typecho-cli submit \
  --title "文章标题" \
  --text "Markdown 正文" \
  --category "分类名" \
  --tags "标签1,标签2,标签3" \
  --status publish

# 更新文章；仅传需要修改的字段
python3 <技能目录>/typecho-cli update \
  --cid <文章ID> \
  --title "新标题" \
  --text "完整新正文" \
  --category "分类名" \
  --tags "标签1,标签2,标签3"

# 删除文章
python3 <技能目录>/typecho-cli delete --cid <文章ID>
```

`submit` 与 `update` 还支持 `--slug`。当前 CLI 的 `submit` 默认状态为 `publish`，但仍应显式传 `--status publish` 表达发布意图；不要依赖默认值处理审核状态。

## 新建文章

1. 按“配置预检”确认配置可用；保留预检时 `categories` 返回的分类结果，不要重复查询。
2. 用 `list` 检索已有文章。若只是修改同一篇文章，转更新流程；若是从同一项目衍生出的独立内容，确认不是重复后仍可新建。
3. 若涉及创作、改写或脱敏，先完成相应编辑流程。
4. 从预检返回的分类中选择；尚未查询分类时再执行 `categories`。没有合适分类时与用户沟通，不要强行选择。
5. 用户要求直接发布时，执行 `submit --status publish`。
6. 记录返回的 `cid`，用 `get --cid` 核对标题、正文、分类、标签和 `status`。
7. 能访问公开页面时再检查实际渲染。优先从博客首页或已有页面获取实际链接；已确认站点使用固定 CID 链接规则时可直接按该规则访问。不要凭 `slug` 猜测并连续尝试不同地址。
8. 无法访问公开页面时，如实说明读回核验已完成，不要宣称已验证公开页面。
9. 反馈文章链接和 `cid`。

## 更新文章

1. 通过 `list` 或已知 `cid` 定位文章，并用 `authorName` 或文章归属确认它归本账户管理。
2. 执行 `get` 获取线上最新完整原文，不以本地旧草稿替代。
3. 明确修改范围；只改标题、标签或分类时，不要顺带重写正文。
4. 修改正文时，在完整原文上完成变更。局部替换若不能唯一定位，停止并重新核对，不要猜测。
5. 只把需要变更的字段传给 `update`；正文参数必须包含修改后的完整正文。
6. 再次 `get` 核验；用户关心页面效果时检查公开页面。
7. 简要反馈实际变更，不要把未修改内容描述成已优化。

同主题文章属于其他账户时不要尝试绕过 403，与用户沟通处理方式。

## 删除文章

1. 通过 `cid` 定位目标并确认归属。
2. 明确提醒删除不可逆，等待二次确认。
3. 执行 `delete`。
4. 反馈结果；不要继续尝试读取已删除文章来制造无谓报错。

## 超时与重试

CLI 请求可能成功写入但客户端未收到响应。出现网络超时、TLS 错误或连接中断时：

- 新建：先用 `list` 按标题、时间和归属检查是否已经创建；找到后改为读回核验，不要直接再次 `submit`。
- 更新：用 `get` 比较线上内容是否已经变更；未变更才重试。
- 删除：确认仍具备删除授权后，用 `list` 检查目标是否已消失。
- 连续失败时停止重试，报告错误并建议稍后检查博客或 Token 状态。

## 响应与错误

CLI 统一输出 JSON，并以 `success` 表示结果。常见错误：

| HTTP 状态码 | 情况 | 处理 |
|---|---|---|
| 401 | Token 缺失、无效或已吊销 | 检查配置；提醒站长到「管理 → AI Token」检查或重新生成 |
| 403 | 文章不属于当前 Token 账户 | 不要重试或绕过，与用户沟通 |
| 400 | 标题或正文为空 | 补全字段 |
| 400 | 文章不存在 | 核对 `cid`，不要重复请求同一路径 |
| 400 | 分类不存在 | 重新执行 `categories`；无合适分类时与用户沟通 |
| 400 | 内容命中敏感信息规则 | 替换为安全占位符后重试 |
| 400 | 没有需要更新的字段 | 至少传入一个实际修改字段 |

未带 HTTP 状态码的网络错误按“超时与重试”处理，不要把它当成文章不存在。

## 技术限制

- 正文不超过 50000 字符；超长时先与用户确定拆分方式。
- 不支持通过本 CLI 上传图片；使用可公开访问的外部图片 URL 和标准 Markdown。
- 插件自动处理 Markdown 标记，传入标准 Markdown 正文即可。
- 插件的敏感信息拦截不能替代人工脱敏；公开文章还需检查内部地址、账号、邮箱和凭据。
- 删除永久生效，不提供回收站语义。
